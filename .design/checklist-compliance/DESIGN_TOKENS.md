# Design Tokens: Checklist Compliance Pass

_Feature slug: `checklist-compliance`_ · Written 2026-08-21

> **No token file is generated by this pass, and that is the deliverable.**
>
> The authoritative token file is **`static/css/tokens.css`** (183 custom properties),
> derived from **Warm Minimalism** per

### Breakpoints are comments, not custom properties — on purpose

The skill's template lists `--breakpoint-*` as tokens. `tokens.css` instead documents
them in a comment block (375 / 768 / 1024 / 1280 / 1536). **This is correct and must not
be "fixed":** CSS custom properties are not valid inside `@media` query conditions —
`@media (min-width: var(--breakpoint-md))` does not work in any browser. A token nothing
can consume is worse than a documented constant, because it implies a contract the
stylesheet cannot honor.

### Dark mode structure

Already matches the skill's rules, and slightly improves on them:

- Dark values are defined **exactly once** as inert raw `--dark-*` tokens, then mapped
  onto the semantic names by two blocks. Single source of truth for the palette while
  still supporting both an explicit choice and the system preference.
- Path 1: `[data-theme="dark"]` — the explicit choice, set pre-paint.
- Path 2: `@media (prefers-color-scheme: dark) { :root:not([data-theme]) }` — `auto`.
  Scoped so an explicit *light* choice always wins, and so **dark keeps working with
  JavaScript disabled**.
- Designed warm charcoal (`#1c1917`), never an inversion. Accent lightened for dark
  (`#e08a63`). Shadows are separate, darker and more transparent — not reused from light.
- `color-scheme` set per path so form controls and scrollbars follow.

The skill suggests `:root:not([data-theme="light"])` for path 2; the existing
`:root:not([data-theme])` is stricter and reaches the same result, since path 1 already
owns the explicit-dark case. No change.

## What the new components consume

Three visual additions land in this pass. Every one resolves to existing tokens.

| Addition | Tokens consumed | New tokens needed |
| --- | --- | --- |
| **External-link icon** | `currentColor` (inherits the link's own color); sized in `em` so it tracks the adjacent text | **None** |
| **`.visually-hidden`** | none — pure `position`/`clip-path` geometry | **None** |
| **Footer sticky-to-bottom** | none — `100dvh` + flex mechanics | **None** |

On the icon: inheriting `currentColor` and sizing in `em` is not laziness, it is what
keeps it correct in both themes and at every type size for free. A dedicated
`--icon-size-*` token would be a new contract bought for one consumer.

On `100dvh`: a layout mechanic, not a design decision. Tokenizing a viewport unit
would imply it is tunable, which it is not.

## Measured contrast (WCAG 2.1 AA)

Computed numerically from the shipped hex values — not eyeballed, not inherited from the
earlier review. `checklist.md` §8 requires body/UI ≥ 4.5:1 and treats warm palettes as a
contrast trap, so every pair is re-measured in **both** themes.

**17/17 pass. No failures, so no token change is justified on contrast grounds.**

The gold/warm contrast trap §8 warns about was already handled: the light link and
accent both sit at 5.42:1 rather than the ~3:1 a naive terracotta would give.

**Tightest margins — the regression watch list.** These are the pairs a future tweak
would break first:

1. `text-tertiary` on `bg-tertiary` (dark) — **4.88:1**, 0.38 above the floor.
2. `text-secondary` on `bg-tertiary` (light) — **5.03:1**.
3. `text-tertiary` on `bg-primary` (light) — **5.16:1**.

Any darkening of a dark well or lightening of light meta text needs re-measuring.

**External-link icon contrast:** footer links render at `--color-text-secondary`
(5.54:1 light / 7.55:1 dark). The icon inherits that via `currentColor`, so it clears the
3:1 non-text UI threshold with room to spare — and it is `aria-hidden` with a
visually-hidden text equivalent, so it never carries meaning by itself.

## Verification method

Ratios computed with the WCAG 2.1 relative-luminance formula (sRGB, the 0.03928
linearization threshold) over the literal hex values in `static/css/tokens.css`.
Script: `scratchpad/contrast.py`. Reproducible; not a judgement call.

The design review phase re-checks these in the browser with axe-core, targeting **0
violations**, which also catches anything composition introduces that raw pairs cannot
predict (overlapping backgrounds, the `--glow` gradient behind text).
